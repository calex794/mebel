# Мебель на заказ — каркас сайта

Сайт для сбора заявок на корпусную мебель высокого класса по индивидуальным проектам в **Стерлитамаке, Салавате и Ишимбае**. Не интернет-магазин, без конструктора и расчёта цены.

## Что реализовано

- Главная страница с акцентом на качество и призывом оставить заявку.
- Разделы «Услуги», «Наши работы», «Статьи», «Контакты».
- Форма заявки (телефон обязателен, имя/пожелания — нет), запись в БД.
- Админка Django: заявки, проекты с несколькими фото, услуги, статьи, контакты, тексты, первый экран.
- Отдельные адреса и SEO-поля для страниц, sitemap.xml и robots.txt.
- Адаптивная вёрстка; отсутствие вымышленных работ/отзывов.
- CSRF, серверная валидация и **простой** лимит заявок (для продакшена нужен общий Redis-кеш и настройка обратного прокси).

## Локальный просмотр сайта и панели управления

Эта возможность **только для вашего компьютера**; сервер или домен не нужен. Не используйте её для публичного приёма заявок.

Нужны Docker и Docker Compose, а также Python 3.11+ для подготовки секрета:

```bash
python scripts/prepare_preview.py
docker compose -f compose.preview.yaml up -d --build --wait
docker compose -f compose.preview.yaml exec site python manage.py createsuperuser
python scripts/smoke_preview.py
```

После этого:

- Сайт: http://127.0.0.1:8000/
- Панель управления: http://127.0.0.1:8000/upravlenie/

Введите логин и пароль, которые задали в `createsuperuser`. В разделе «Настройки сайта» заполните название, телефон, адрес и фото первого экрана. Затем добавьте услугу, настоящую работу с несколькими фотографиями и статью. Ставьте «Опубликовано», когда содержание готово. Входящие заявки отображаются в разделе «Заявки».

Загруженные фотографии и база сохраняются между перезапусками в отдельном томе `preview_data`; они не коммитятся в Git. Для остановки: `docker compose -f compose.preview.yaml down`. **Не запускайте `down -v` — эта команда удалит сохранённые данные.**

Порт в `compose.preview.yaml` привязан к `127.0.0.1`: с другого устройства по сети предпросмотр недоступен. Не заменяйте его на `0.0.0.0` и не открывайте наружу. `DEBUG=1` и встроенный сервер Django непригодны для публичной эксплуатации.

## Размещение на сервере

Конфигурация HTTPS + PostgreSQL + резервное копирование: [инструкция](deploy/README.md). Для запуска потребуются домен и отдельный сервер. Публичный запуск запрещён до готовности политики персональных данных и проверки восстановления.

## Как запустить локально

Нужен Python 3.11+.

\`\`\`bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
\`\`\`

На Windows: \`.venv\Scripts\activate\` вместо \`source .venv/bin/activate\`.

- Сайт: http://127.0.0.1:8000/
- Управление: http://127.0.0.1:8000/upravlenie/

После входа откройте **«Настройки сайта» → Добавить**, укажите название, телефон и фото первого экрана (создаётся одна запись). Затем заполняйте «Услуги», «Наши работы», «Статьи», включая «Опубликовано» для видимости на сайте. При добавлении русских названий адрес страницы создаётся автоматически; при необходимости его можно изменить.

Проверки: \`python manage.py check\`, \`python manage.py test\`. Для продакшена дополнительно \`python manage.py check --deploy\`.

## Перед запуском в интернет

1. Настроить настоящий домен, HTTPS, непредсказуемый \`DJANGO_SECRET_KEY\`, \`DEBUG=0\`, \`DJANGO_ALLOWED_HOSTS\` и при необходимости \`DJANGO_CSRF_TRUSTED_ORIGINS\`.
2. Не выставлять Django runserver в интернет; использовать Gunicorn и Nginx/Caddy. Пример: \`gunicorn mebel_site.wsgi:application --bind 127.0.0.1:8000\`. Прописать постоянное хранение медиа и резервные копии БД/фотографий; \`python manage.py collectstatic --noinput\`.
3. Для нескольких процессов/серверов: PostgreSQL + общий Redis-кеш для ограничения заявок, безопасное определение IP на обратном прокси, фильтрация ботов/спама.
4. **Обязательно:** заменить черновую страницу \`/privacy/\` полной политикой обработки персональных данных. Проверить правовые требования к форме и обработке заявок в РФ, включая применимые требования к местонахождению базы персональных данных.
5. Добавить действительные контакты, реальные фотографии, подтверждённые преимущества. Не оставлять неподтверждённых обещаний.
6. Продумать отдельную раздачу файлов \`media/\` через сервер, с запретом выполнения загруженного содержимого, проверкой форматов и лимитов. Не полагаться на DEBUG-раздачу медиа в продакшене.
7. Подключить аналитику и при необходимости уведомления о новых заявках.
8. До полноценной эксплуатации создать и проверить начальную миграцию \`python manage.py makemigrations catalog\`; коммит сгенерированной миграции обязателен.

## Политика данных и согласие (обязательно до запуска)

В `/upravlenie/` появился раздел «Политика обработки данных». Создайте новую редакцию и заполните **реальные, проверенные** сведения об операторе (ФИО/название, статус, адрес, контакты и применимые реквизиты), цели, категории данных и субъектов, правовые основания, действия и способы обработки, сроки хранения, прекращение обработки и удаление, отзыв согласия, меры защиты, получателей и отдельный текст согласия. Реквизиты не подставляются автоматически.

Пока нет опубликованного документа, обе формы скрыты, а отправка заявок возвращает HTTP 503. **Публикация выполняется вручную** действием «Опубликовать выбранную редакцию» в списке документов; обязательные поля проверяются. Публикация означает лишь техническую активацию, не юридическое одобрение. После публикации текст и обозначение версии не редактируются: для изменений создайте новую редакцию. Действие «Остановить приём» отключает формы. Публичный адрес `/privacy/` показывает действующую редакцию, `/privacy/?version=...` — прежнюю опубликованную.

При явном согласии заявка сохраняет время, номер редакции и ссылку на неизменный документ. Устаревшая версия формы отклоняется HTTP 409, отсутствие согласия — HTTP 400. Старые заявки мигрируют без фиктивного номера версии (пустое поле). Тексты публикуются как обычный текст, без доверенного HTML. Проверки: `python manage.py makemigrations --check --dry-run` и `python manage.py test catalog.test_privacy_consent catalog.tests`.

**Это не утверждённая юридическая политика.** Перед публичным запуском оператор должен проверить содержание и применимые обязанности по 152-ФЗ, локализации, уведомлению Роскомнадзора, срокам хранения, архивам/резервным копиям и обработке обращений об отзыве. Сайт не реализует автоматическое удаление/отзыв: указанная процедура должна исполняться оператором с учётом применимых требований.


### Ручная регистрация подтверждённого отзыва

При обращении человека об отзыве согласия оператор должен проверить его связь с заявкой по своему регламенту. После проверки в панели «Заявки» выберите соответствующую заявку и действие «Подтвердить отзыв согласия». Система фиксирует дату регистрации, переводит заявку в состояние «Согласие отозвано» и запрещает изменить её состояние обратно обычными средствами панели управления. Повторное действие не меняет первоначальную дату; версия и время исходного согласия сохраняются. <b>Не отмечайте чужие заявки без проверки.</b>

Отметка не означает удаления данных или юридического решения о сроке хранения: оператор отдельно определяет применимые основания, срок ответа, дальнейшие действия и выполнение удаления, включая резервные копии. Публичную форму для отзыва не добавляли, чтобы не принимать неподтверждённые требования от третьих лиц.


### Очистка контактных данных по подтверждённому отзыву

После проверки личности обратившегося и регистрации отзыва оператор оценивает, не нужно ли сохранить сведения по другому законному основанию. Если данные можно удалить, в панели «Заявки» нужно выбрать **одну** заявку в состоянии «Согласие отозвано» и действие «Очистить личные данные отозванной заявки». Появляется отдельное подтверждение: необходимо отметить проверку законных оснований, принять к сведению ограничения по резервным копиям и ввести фразу с номером заявки. После подтверждения атомарно очищаются поля `phone`, `name`, `message`, `source` и сохраняется `erased_at`. Исходная версия согласия и даты остаются для минимального технического учёта, без контактов посетителя. База запрещает повторно заполнить очищенные поля и перевести такую заявку в обычную обработку; повторный запуск очистки не меняет дату.

Это **очистка данных заявки в основной базе**, а не автоматическое выполнение всех требований об удалении. Перед первым запуском необходимо установить правила сроков хранения, пересмотреть доступ к журналам и экспортам и настроить отдельную работу с архивами и резервными копиями. Восстановление старого архива может вернуть удалённые данные — после любого восстановления обязательно сверить внешнюю защищённую ведомость выполненных очисток и повторно очистить такие записи до открытия доступа. Обычное удаление заявки через панель запрещено, чтобы не обойти процедуру и не потерять след её исполнения.

Проверки: `python manage.py test catalog.test_lead_erasure catalog.test_privacy_consent`.

Дополнительно очищаются сохранённые в таблице `django_admin_log` текстовые поля журнала изменений, относящиеся к данной заявке (предыдущее представление объекта и описание изменения): они могут содержать телефон. Сама запись о действии остаётся без контактных данных. **Это не затрагивает внешние файлы журналов сервера, историю браузера и созданные ранее архивы**.
